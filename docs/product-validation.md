# Validate Snapkit with developers

The November 6 interface revision prioritizes a clear multi-device workflow, visible selection feedback and actionable setup diagnostics. Do not present a design score as measured product effectiveness.

Use consenting Flutter and React Native developers with their own non-sensitive test projects. Include both a new and an existing user, macOS and Windows, and a participant who normally uses only one device. No automatic source-code or session-recording collection is required.

| Task | Record |
| --- | --- |
| Explain Snapkit after viewing the landing | What it does, who it serves, what they expect F5 to do |
| Connect a project and resolve one missing SDK | Completion, time, errors and assistance needed |
| Start two devices and select them for IDE debugging | Completion and whether the selection feedback is understood |
| Make one UI change and check both screens | Actual IDE/framework behavior; compare with their existing workflow |
| Return later to the same workspace | Whether setup guidance obstructs work; ability to reopen it |
| Capture a screenshot or inspect device logs | Whether they distinguish device logs from the IDE debug console |

Measure the same task with and without Snapkit on the same project/device set. Report completion rate, median task time, failures, assistance and participants' reasons to use or decline the app. Record platform/framework limitations separately. Do not invent time-saving percentages, testimonials or universal usefulness claims.

Release validation remains separate: browser tests, platform startup/packaging, update integrity and genuine SDK/device smoke tests. Automated demo coverage is not evidence that a real Flutter/RN build succeeds on every host.
