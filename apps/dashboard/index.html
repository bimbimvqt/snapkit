START WITH CONFIDENCE

Your first session, step by step.

From a fresh install to a repeatable multi-device workflow.

01 · Prepare your computer02 · Connect your project03 · Prepare a device04 · Debug in your editor05 · Save your everyday device set06 · Read device system logs07 · Capture and share a result08 · When something needs attention
01

Prepare your computer

Install Flutter and Android SDK for Android devices on macOS or Windows. For iOS Simulator, use macOS with Xcode, its command-line tools and an installed iOS runtime. Windows cannot run iOS Simulator.

Check each tool, accept Android SDK licenses and save custom SDK paths in Preferences if detection fails.
02

Connect your project

Choose the folder containing pubspec.yaml. Import a VS Code debug profile or select the flavor, Dart entrypoint and defines file. Snapkit stores these choices locally without changing your source or launch.json.

Moved your project? Choose its new folder again. Saved device sets belong to the original folder; Snapkit does not scan your disks to relocate source code.
03

Prepare a device

Use Add device to choose a compatible model and OS, then start it. For Android phones, enable USB debugging and approve this computer. For iPhone, enable Developer Mode, trust your Mac and configure signing in Xcode.

Android Wi-Fi: pair and connect using Android Studio Wireless debugging first. Keep both devices on the same stable network. Wi-Fi speed depends on your network; USB can be faster.
04

Debug in your editor

In VS Code, Cursor or Antigravity, install Snapkit Debug Sync and the Dart/Flutter extensions. Open the same project, select online devices in Snapkit and press F5 in your normal Flutter profile.

Android Studio and IntelliJ use their own device selector and debug controls. Hot Reload, Dart output and DevTools stay in your IDE. A new Snapkit selection applies to the next debug run.
05

Save your everyday device set

Create a named set for the current project, such as Phone + tablet. Include virtual devices that are currently off. Start the set to boot up to two devices at a time and follow each result.

Physical phones must already be connected. Missing devices are reported individually. Use Select ready devices for IDE after startup; starting a set does not alter an existing debug session.
06

Read device system logs

Select an online Android device or iOS Simulator, then start logs. Search by app name, package or message and filter warnings/errors. Pause following to read a line, or export the visible filtered log.

These are system logs, not the Flutter Debug Console. Keep the IDE open for Dart print output. Snapkit retains the latest 1,000 lines per stream and stops streams without a viewer after one minute.
07

Capture and share a result

Take a PNG screenshot or record an MP4 from a supported online device. Stop recording to finalize the file before downloading. Captures are stored separately for each project in Snapkit data.

Recordings are limited to 3 minutes, with at most two running at once. Physical iPhone capture and logs require Xcode or QuickTime. Recordings do not include audio; protected screens may appear blank.
08

When something needs attention

If a device is missing, unlock it, check trust or USB debugging and refresh Devices. If tools are missing, verify SDK paths. If debug targets do not apply, check the project folder and Snapkit extension in your editor.

Internet is required for account verification. Device commands and source stay on your computer. Keep enough free disk space for emulator data and recordings; delete saved captures when no longer needed.

How TestFlight works
  1. Choose the environment.

    Dev and prod use your Flutter flavors, entrypoint and defines. TestFlight builds always use release mode.

  2. Create a signed IPA.

    Xcode archives and exports an App Store IPA on this Mac. Your iOS app needs an Apple Developer team, distribution signing and an App Store Connect app with the matching bundle ID.

  3. Upload when ready.

    Configure your App Store Connect API key below, then confirm the saved IPA to upload. Upload does not rebuild or change the selected environment.

  4. Wait for Apple, then invite testers.

    Apple validates and processes the build. Manage test groups and export compliance in App Store Connect; external testing may require Beta App Review. TestFlight builds expire after 90 days.

Get a Team API key in four steps
Team keys may access all apps in the organization according to their assigned role. Use only a key you are authorized to manage and keep it out of source control.
  1. 01
    Check your account access
    Team keys are created by the Account Holder or an Admin. If API access is not enabled, the Account Holder opens Users and Access → Integrations → App Store Connect API, chooses Request Access, accepts the terms and clicks Submit. Wait for Apple’s approval before generating a key.
  2. 02
    Generate a team API key
    Open Users and Access → Integrations → App Store Connect API → Team Keys. Choose Generate API Key (or +), give it a name and select a role that can upload builds, such as Developer or App Manager.
  3. 03
    Download the private key once
    Choose Download API Key and keep the original AuthKey_KEYID.p8 filename. Apple offers this download only once. If the file was lost, an authorized team admin must revoke the old key and create a replacement.
  4. 04
    Copy the IDs, then connect
    Copy Issuer ID from the Team Keys page, then choose your .p8 file in the form. Snapkit fills Key ID from its filename and suggests Team ID from your project. After connecting, select the matching app before uploading.

Use your own Apple account
A team invitation does not provide a .p8 file or permission to manage team keys. You can upload with Xcode when your account has the required app access and upload role. No API key or Issuer ID is needed for this route.
  1. 01
    Sign in with your own Apple account
    In Xcode → Settings → Accounts, add the account invited to the team. In App Store Connect, check that this account can access the app and upload builds. Signing certificates and provisioning must also be available.
  2. 02
    Create an archive for the right environment
    Open ios/Runner.xcworkspace in Xcode. Choose the dev/prod scheme, select a generic iOS device destination and use Product → Archive. If you already built an IPA in Snapkit, open the matching .xcarchive under build/ios/archive/ instead.
  3. 03
    Upload from Organizer
    Open Window → Organizer → Archives. Check the app, version and build number, then choose Distribute App → App Store Connect (or TestFlight & App Store) → Upload. Select the correct team and review Apple’s confirmation screens.
  4. 04
    Wait for processing, then invite testers
    After upload, open the app’s TestFlight tab in App Store Connect. Resolve validation or export-compliance questions, then assign the build to a test group. External testing may require Apple review.
Open App Store Connect

Stuck on a step?
I cannot see Integrations or Issuer ID
Check that you selected the correct organization and Team Keys tab. API access may not be enabled, or your role may not manage team keys. Use the Xcode route if you are an invited member without API access.
There is no Download API Key button
A team key can only be downloaded once. An invitation does not include its private key, and a key already downloaded cannot be downloaded again from Apple. Use a replacement key you are authorized to manage, or upload with Xcode.
I have an Individual API key
Individual keys use a different authentication flow and do not have a team Issuer ID. This Snapkit version supports Team API keys for in-app upload. Use Xcode for now; do not put Team ID into the Issuer ID field.
Will this change my build or publish my app?
Opening this guide or connecting a key does not build or upload anything. IPA builds still run locally. Snapkit uploads only after you confirm a saved IPA; Apple processing and test groups remain in App Store Connect.
